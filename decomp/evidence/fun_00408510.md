## ABI and object layout

The final `ret 4` proves one 32-bit stack argument. ECX is retained in ESI as
the destination object and EAX is explicitly reloaded from ESI after the
delegate call:

~~~text
FUN_00408510_String* FUN_00408510(
    FUN_00408510_String& destination,
    const char* source)
~~~

The object is the same SSO holder used by the recovered 82E0/83C0 family:

- opaque allocator/state dword at `+0x00`;
- storage union at `+0x04`;
- logical length at `+0x14`;
- capacity at `+0x18`.

Native 8510 writes only:
- capacity = 15;
- length = 0;
- first inline byte = NUL.

It deliberately does **not** write the opaque dword at `+0x00` or the
remaining 15 storage bytes.

## Length scan and 83C0 delegation

The source pointer is loaded before object initialization, then the object is
reset to empty SSO, and only afterwards does the native byte loop scan for the
terminating NUL.

The loop computes the exact C-string length as:

~~~text
cursor = source
do {
    byte = *cursor++
} while (byte != 0)
length = cursor - (source + 1)
~~~

It then calls already-recovered `FUN_004083C0(destination, source, length)`.

This ordering matters when the supplied pointer aliases the destination's
prior inline bytes: the constructor writes NUL at `this+4` before the scan.
The portable test suite explicitly covers that ordering.

There is no native null-source guard. A null source would be dereferenced by
the byte loop, so the recovery does not invent a nullable-input branch.
