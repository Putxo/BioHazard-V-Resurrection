# Exact-attachment recovery: 00408B50 through 00408E00

## Target and scope

Only the locally supplied 19,977,216-byte PE32 executable with SHA-256
`323d1aabccc74505745588097e2b298b14e114393bfc24f6830e98b658e67815`
was analyzed. No original EXE, DLL, asset, object, or other build product is
included in this contribution. Fourteen non-overlapping bodies account for
**632 instruction bytes**, excluding post-return padding.

This is original C++ recovery in an explicit **target-address memory adapter**.
It does not implement a final native x86 calling interface or the external
callees. Missing services are not replaced with success values/no-ops. The
caller must supply real memory/call adapters; the test fixtures are deliberately
identified as fixtures. FAST_PASS / subsequent CI-validation is the scope;
CONVERTED, VERIFIED, MATCHED, LINKED and whole-game completion are not claimed.

## Semantics that must not be simplified away

A handle's sign is tested as a 32-bit sign bit, not by a host-sized pointer
comparison. BE0 reloads **both the handle and manager after its first call**.
A callback may make the handle negative: the original still performs the
second call, without another validity test, and clears the handle afterward.
B90 status 2 preserves callback changes; status 0 overwrites the handle with -1.

B50's NEG/SBB sequence maps every nonzero mode word to 0x9D, including words
with bit 31 set. CD0 observes only its low input byte: 0x100 behaves like zero.
CF0 instead observes the entire input word: 0x100 selects the nonzero bank.

CF0 loads each table entry and singleton at the point shown in the binary,
not as a snapshot before all four requests. Each non-null returned resource
is delivered and then released with that same resource as receiver. A null
result skips both operations. Later requests still occur. The fourth delivery
uses global 0x016E2EFC, unlike the first three's 0x0165A1F0.

DE0 preserves every base-initialized word other than the three explicit
writes. E00 exposes the intermediate vtable during the imported cleanup call.
The import at IAT 0x0137119C is KERNEL32!DeleteCriticalSection, verified from
the same attachment's import table.

## Validation actually performed

GCC and Clang ASan/UBSan each passed **2,942 explicit checks** with assertions
independent of NDEBUG. The tests cover all fourteen entrypoints, signed
boundaries, noncanonical boolean words, all low-byte values under four upper
word patterns, all sixteen resource-null combinations, callback mutations,
field preservation and unreadable memory beyond genuine early exits.

A separate bounded integer-instruction interpreter decoded the selected bytes
with objdump and compared the C++ against **2,371 scenarios**, **9,597 ordered
non-stack memory/call events**, final memory and meaningful returns. All **26/26
conditional branch edges** were covered. Stack cleanup and callee-saved registers
were checked in the instruction model. External functions use a shared explicit
fixture: this verifies wrapper behavior under that model, not their real bodies.
It is not native x86 execution or independent whole-game equivalence proof.

The C++ also compiled into Windows x86 COFF with Clang. That object was not
linked, executed, or uploaded. Source-only CI checks reject changed source
hashes, wrong input, unmapped fixture memory, unknown callees and unsupported
instructions. CI never receives or downloads the original executable.

## Candidate membership without denominator changes

An independent local reconstruction reproduces the frozen V6 **79,782**-address
union exactly in aggregate: 69,076 post-padding starts, 40,912 non-.text aligned
pointer-sequence targets, and 19,195 direct roots including the PE entry point
(19,194 actual direct CALL targets). All fourteen addresses belong to the union.
B50, DE0 and E00 have the explicit aligned post-padding evidence; the other
eleven also have decoded direct-call evidence.

The previous local CSV itself was not available in this session. Therefore the
report explicitly identifies an independent set reconstruction, **not a claim
that the original CSV was read byte-for-byte**. Eight recorded direct-root
row anchors also match when counting the CSV header. No canonical file,
denominator, historical exclusion or inventory baseline is changed. Candidate
membership is not itself a claim that every potential start is a true function.

## Reproduce

From the repository root, ordinary builds include the batch and its CTest:

```sh
cmake --preset dev
cmake --build --preset dev
ctest --preset dev
```

For the additional local-only input-bound checks:

```sh
python tools/verification/verify_batch_00408b50.py --exe "/path/to/exact.exe" --report local-differential.json
python tools/verification/reproduce_v6_for_batch_00408b50.py --exe "/path/to/exact.exe" --report local-membership.json
```

Neither command launches the input executable. The second does a full .text
linear disassembly for direct-call evidence; it does not decompile or count the
remaining candidates as implemented.

## Remaining boundaries

The adapter exposes calls at 004B14A0, 004E6F10, 004B6EC0, 004B1470, 004B1430,
00D14C10, 004AFD20, 004AFD40, 004B13F0, 004C5060, 00D25060 and 00D02A20, plus
the cleanup import. Their real implementations, exceptions, native ABI and
runtime integration remain outside this batch. CF0's ret 4 / unused ECX is
stdcall-compatible; its original source-level member/nonmember declaration is
not established. DD0 also ignores ECX. Forwarded EAX values are retained without
claiming original source return-type names.
