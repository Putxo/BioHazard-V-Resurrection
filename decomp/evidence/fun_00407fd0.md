## Temporary construction and refcount behavior

The native routine uses its caller-owned suffix argument slot as temporary
storage for a `FUN_00402360_String`:

1. pass the suffix to recovered `FUN_00402360`, with ECX pointing at the
   same stack slot that originally held the suffix pointer;
2. reload the resulting block pointer from that slot;
3. if it is null, return immediately with destination untouched;
4. if destination is null, adopt the incoming block and increment its
   refcount;
5. otherwise call opaque native helper `0x01199FB0` with current and incoming
   blocks;
6. decrement/release the old destination block, freeing through global
   allocator `0x01652F28` virtual slot `+0x18` only when its refcount reaches
   zero;
7. install the combined block;
8. decrement/release the temporary incoming block using the same contract.

The increment in the empty-destination branch is balanced by the final
temporary release, leaving one live destination reference.

## Opaque concatenate helper

The `0x01199FB0` call is the same allocator-backed concatenate helper already
cross-checked by the recovered D10 path. Its observed contract is:

- take old and incoming refcounted string blocks;
- allocate `old_length + incoming_length + 0x0C` bytes at alignment
  `0x10`;
- initialize refcount to one and length to the sum;
- copy old payload first and incoming payload second;
- terminate with NUL;
- return the combined block.

FD0 keeps that out-of-scope helper behind its own injected service so the
function can be published independently of D10/D90.
