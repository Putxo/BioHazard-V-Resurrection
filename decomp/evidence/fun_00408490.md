## Base constructor, RTTI and object layout

The native call at `0x01251B2C` is fully visible in the same executable:

~~~text
01251B2C  mov eax,ecx
01251B2E  and dword ptr [eax+04h],0
01251B32  and dword ptr [eax+08h],0
01251B36  mov dword ptr [eax],01541FACh
01251B3C  ret
~~~

Thus the base constructor zeroes offsets `+0x04` and `+0x08` and installs
the base vtable before 8490 overwrites the vtable with `0x01541F54`.

MSVC RTTI independently identifies the hierarchy:

- vtable `0x01541FAC` has COL `0x01563298`, whose type descriptor is
  `0x015672F4 == ".?AVexception@std@@"`;
- vtable `0x01541F54` has COL `0x015631AC`, whose type descriptor is
  `0x015674B0 == ".?AVlogic_error@std@@"`;
- the adjacent derived vtables used by the two direct callers identify
  `std::length_error` and `std::out_of_range`.

The recovered object layout is therefore:

- `+0x00`: final `std::logic_error` vtable;
- `+0x04`: base message pointer/state, zeroed by the base constructor;
- `+0x08`: base ownership flag/state, zeroed by the base constructor;
- `+0x0C`: embedded 28-byte SSO string object;
- embedded string length at object `+0x20`;
- embedded string capacity at object `+0x24`;
- total observed object size: `0x28`.

8490 explicitly initializes only the embedded string's length, capacity and
first inline byte. The first dword of the embedded string at object
`+0x0C` is not written by this constructor and is intentionally preserved by
the portable reconstruction.

## ABI and recovered behavior

The final `ret 4` proves one 32-bit stack argument while ECX is the object
being constructed:

~~~text
FUN_00408490_Object* FUN_00408490(
    FUN_00408490_Object& object,
    const FUN_004082E0_String& source)
~~~

The behavior is:

1. Apply the exact observable base-constructor state from `0x01251B2C`.
2. Install the final `std::logic_error` vtable `0x01541F54`.
3. Address the embedded string at `this+0x0C`.
4. Set embedded length to zero and capacity to `0x0F`.
5. Write the inline terminating NUL.
6. Call recovered
   `FUN_004082E0(message, source, 0, UINT32_MAX)`,
   which copies the complete source string.
7. Return `this`.

## Direct-call evidence

A complete decoded scan of the exact `.text` section finds exactly **2**
direct calls to `0x00408490`:

~~~text
01251351  call 00408490
01251390  call 00408490
~~~

The first caller builds a temporary SSO string from the literal
`"string too long"`, invokes 8490, then overwrites the returned object's
vtable with the `std::length_error` vtable before throwing it.

The second does the same with `"invalid string position"` and the
`std::out_of_range` vtable.

These callers, together with RTTI, independently confirm that 8490 is the
shared `std::logic_error` construction layer consuming an SSO string.

There are zero raw little-endian absolute `0x00408490` data pointers in the
exact executable.
